# 网银与登记共用的模拟鉴权配置

`bank-transfer-auth.json` 为两端提供相同的共享密钥与协议配置；格式版本为 `3`，使用 36 字符短流水号，已取代旧固定编号及 100 字符长编号。

- `sharedKey`：两端须完全相同的 UTF-8 密钥字符串。
- `algorithm`：`HMAC-SHA256`。
- `payloadPrefix`：当前为 `bank-transfer:v2`，两端须相同。

## 流水号协议

1. 将大于零、最多 12 位整数及两位小数的金额规范为两位小数字符串。例如 `00100.0`、`100` 均为 `100.00`。
2. 每次转账生成 12 字节加密随机因子，以无填充 Base64URL 编码为 16 字符 `nonce`。
3. 签名原文为 `payloadPrefix + "\n" + 金额 + "\n" + nonce`，两个分隔符均为 LF（字节 `0A`）。
4. 对原文的 UTF-8 字节计算 HMAC-SHA256，密钥同样用 UTF-8；取结果的前 12 字节，以无填充 Base64URL 编码为 16 字符签名。
5. 最终编号为 `TR_<nonce>_<signature>`，共 36 个 ASCII 字符。Base64URL 保留大小写，使用 `A–Z`、`a–z`、`0–9`、`-`、`_`。
6. 验证时按固定长度提取 nonce 和签名，使用相同金额和密钥重新计算并比较签名。不能任意按 `_` 分割，因为两段编码本身也可能含 `_`；可用正则 `^TR_([A-Za-z0-9_-]{16})_([A-Za-z0-9_-]{16})$` 提取。

例如金额 `100.00` 的签名原文如下（最后一行后不追加换行）：

```text
bank-transfer:v2
100.00
<16字符Base64URL随机因子>
```

二次确认弹窗与成功回执使用同一个编号；取消后重新发起会生成新随机因子。登记在 iframe 内按填写的金额重新验签；旧固定编号、旧长编号、任意编造/篡改的编号、错误金额或不同密钥不能通过。其它转账字段执行普通表单校验，不参与签名。升级后请重新生成流水号。

原生算法模块为 `WEB/shared/transferReference.mjs`，独立对照测试为 `WEB/tests/transfer-reference-test.mjs`；后续 CS 端可按上述协议实现相同校验。更新配置后需重新构建 WEB，并同步 CS 端配置。

此方案用于靶场模拟，密钥随前端分发且可查看。96 位随机因子让重复概率极低，签名截取为 96 位；无状态方案不提供严格的全局历史去重、单次使用或真实支付鉴权。
